# Training Runbook

## Supported workflow

Use Windows for policy/data work and either native CUDA PyTorch or WSL2 Ubuntu for training. WSL2 is the preferred reproducible path for an NVIDIA GPU because the QLoRA stack depends on compatible PyTorch, CUDA, and bitsandbytes builds. Docker is optional; do not hide host-driver incompatibility inside a container.

The proposed 8B run requires at least 24 GiB VRAM. A 32 GiB NVIDIA GPU provides more margin for 4,096-token QLoRA. The exact batch, sequence length, and optimizer must still pass a measured smoke test; a VRAM estimate is not proof.

## Core validation

From the repository root:

```powershell
$env:PYTHONPATH = "src"
python -m biblical_moral_ai validate
python -m unittest discover -s tests/python -v
```

`validate` checks implementation integrity. `preflight` is expected to return blocked until approved text corpora and the minimum reviewed datasets exist:

```powershell
python -m biblical_moral_ai preflight
python -m biblical_moral_ai cuda-check --minimum-vram-gib 24
```

## Environment

Create a dedicated Python 3.11 or 3.12 virtual environment in WSL2. Install a CUDA-enabled PyTorch build using the command generated by the official PyTorch selector for the host driver, then install this project with the training extra. Do not assume the generic PyPI command selected the correct CUDA build.

Record `nvidia-smi`, driver version, CUDA runtime reported by PyTorch, GPU name, VRAM, Python version, package lock, git commit, config hash, and data hashes. The launcher writes these details to `run_manifest.json`.

## Dataset preparation

1. Approve and pin every corpus in `configs/data/source_registry.json`.
2. Create reviewed records matching `schemas/sft-example.schema.json` and `schemas/preference-pair.schema.json`.
3. Validate chosen answers through the full inference pipeline.
4. Materialize message records only after approval.
5. Split by scenario family and derivation lineage, deduplicate, hash each file, and update `data/registry/dataset_manifest.json`.
6. Keep sealed acceptance content with an independent custodian.

Candidate doctrine outlines are not training data and never count toward minimums.

## SFT

Inspect the proposed run without loading weights:

```powershell
python -m biblical_moral_ai train configs/training/apertus_8b_qlora.json
```

After all gates pass, run a two-step smoke test:

```powershell
python -m biblical_moral_ai train configs/training/apertus_8b_qlora.json --execute --smoke-test
```

Review loss, peak VRAM, throughput, checkpoint readability, sample structure, citation behavior, and commandment regressions before a full run. Then remove `--smoke-test`; `--execute` is deliberately required.

## DPO

DPO starts only from an SFT adapter that passed its evaluation and from 1,000 independently reviewed pairs:

```powershell
python -m biblical_moral_ai train configs/training/apertus_8b_dpo.json --execute --smoke-test
```

Never use reviewer affiliation or organizational agreement as a preference reason. Re-run public regression tests after each checkpoint and reserve the sealed set for final acceptance.

## Release

Populate a copy of `evals/results/release_metrics.template.json`, then run:

```powershell
python -m biblical_moral_ai check-release path/to/release_metrics.json
```

Every gate is non-waivable in code. Publish the resulting report, failed-case categories, reviewer method, data/model cards, limitations, and artifact hashes before scholar-facing release.
